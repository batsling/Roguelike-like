# Roguelike Radio

The player's own music, unlocked by playing the real games, played into OBS (or
out of the game window). This is the design and the reasoning; the code is
`scripts/autoload/Radio.gd`, `scripts/ui/RadioScreen.gd` and the `radio` card in
`obs/`.

## 1. What the owner asked for

- Songs unlocked by playing **the game they belong to**. Since October 2026
  (the second ask) a game **earns** songs and **which one is random**: one on
  its **first beat**, one on **every 3rd beat** (the first beat counting
  towards it), and one for **every 5 goals** completed there. It replaced a
  rule per song ("complete X distinct goals in Y", "beat Y X times").
- **A game's first song is its menu song** (the third ask): the first Hades
  song you get is the Hades song tagged `menu`, and the same for every game
  that has one.
- The music is **music the owner already owns**. It is never committed.
- Songs are authored in **the spreadsheet**: name, artist, album, year, game,
  album image and tags. **Every song is tied to its game**: it is only ever
  drawn there.
- **Nothing is unlocked by hand.** A game draws its songs the moment its counts
  earn them, and that includes counts the save already holds.
- It plays **into OBS**, with a setting to play it **from the game window** when
  OBS isn't running.
- **Skip, back, pause and volume** are available from anywhere.
- It plays **the whole time the game is open** (menus and runs), **shuffled**,
  with **tags as stations**.
- A new unlock gets a **toast** in the game and on the overlay, and **plays
  next**.
- **Favourites** (the fourth ask): a ★ on a song stars it, and a **Favourites
  station** plays only starred songs (§5a).

## 2. The `radio` sheet

`tools/Roguelikes.xlsx` → `radio`, generated by `tools/generate_song_tres.py`
into `data/songs/*.tres` (`SongData`). Edit the sheet and regenerate, as for all
content. The sheet was created by `tools/_radio_sheet_setup.py` with one example
row (No Escape, Hades); delete it freely.

| Column | Meaning |
|---|---|
| `Name` | the song's title |
| `Artist` | who made it |
| `Album` | optional |
| `Year` | optional |
| `Game` | the game it belongs to **and is drawn at**: its name as the `games` sheet spells it, or its id. Must be in the catalog. A row with no `Game` is never drawn |
| `File` | the exact file name in the music folder: `.mp3`, `.ogg` or `.wav` |
| `Image` | album art base name under `images2.0/radio/` (blank = the game's cover) |
| `Tags` | comma-separated, lower-cased; every tag is a station. **`menu`** marks the game's menu song, the first song it gives (§3) |

The generator **rewrites** `data/songs/`: a row deleted from the sheet takes its
`.tres` with it. It refuses an unknown game, an audio extension it can't play,
two rows that come out as the same id (`<name> <artist>`, slugified), a sheet
missing any of the eight columns above (by name: a renamed `Tags` would
otherwise read as blank, and every menu song would lose its tag), and a sheet
that still has the retired `Unlock` / `Count` columns
(`tools/_radio_random_unlocks_setup.py` took them off; there is no per-song
rule left for them to hold).

**There is no "blank keeps it locked" any more.** A row used to stay locked
until its `Unlock` was filled in, so a song still being authored could not
start playing on stream. Now any row with a `Game` is in that game's draw. A
row being authored can be left without its `File`: if it is drawn it shows as
"file not found" and never plays, and songs whose file is in the folder are
always drawn first.

## 2a. Filling the sheet from a folder of music

Typing a row per song doesn't scale to a whole music library, and the music is
never uploaded, so the game does the listing: the Radio screen's **Export song
list** button (`Radio.export_library`) walks the music folder, **subfolders
included**, and writes `tools/radio_import.json` (`user://radio_import.json`
from an exported build): every `.mp3`, `.ogg` and `.wav`, its path relative to
the folder, and what the file's own tags say. Godot plays these formats but
reads none of their tags, so `scripts/runtime/AudioTags.gd` does: ID3v2 (2.2 to
2.4) with ID3v1 as a fallback, the Ogg Vorbis/Opus comment packet, and a WAV's
`LIST INFO`. Cover art is seeked past, never read. The list is a few KB however
big the music is, and it is the only thing that has to be uploaded.

`python3 tools/apply_radio_import.py` turns it into rows (`--dry-run` to look
first):

| Column | From |
|---|---|
| `Name` | the title tag, else the file name less its track number and a leading "`<game> - `" |
| `Artist`, `Album`, `Year` | the tags (the album artist when there's no artist) |
| `Game` | **a folder on the file's path that names a game** (innermost first), else the album; soundtrack words don't count, so `Slay the Spire OST/` and `Hades (Original Soundtrack)/` both match. Exact names only, never a guess |
| `File` | the relative path, `Hades/01 No Escape.mp3`. **A `File` may name a subfolder**, so the folder-of-folders can sit in the music folder as it is |
| `Tags` | `menu` when the title says menu, title screen/theme or main theme (§3); else blank |
| `Image` | always blank, so every song shows **its game's cover** (the owner's call: album art isn't worth collecting). The file's own embedded art is never read |

- **It only adds.** A file already on a row is skipped, so the export can be
  re-run whenever music is added. A file whose game it can't tell is added with
  `Game` blank (never drawn) and listed by folder; type the game into the sheet
  or re-run with `--game "Folder=Game"`, which also fills the rows a previous
  run left blank.
- **A row whose `File` isn't in the folder is re-pointed** when a file in it is
  the same song (same `Name` + `Artist`): that is a typo, a rename, or the
  sheet's example row.
- **Two files with the same name and artist** (two games' untagged
  `Main Menu.mp3`) are told apart by the game in brackets after the name, since
  the generator refuses two rows with one id. A true duplicate is skipped.
- It writes through `_xlsx_surgery`, then runs `generate_song_tres.py`. The
  JSON is spent once applied: delete it in the same commit.

## 3. Unlocking

**A game earns songs; the draw decides which.** One rule for every game
(`Radio.earned`, `Radio.earned_for`):

| A game earns a song… | Counts | Source |
|---|---|---|
| on its **first beat** | — | `GameStats.beaten_count(game)` |
| on **every 3rd beat**, the first one counting towards it: beats **3, 6, 9, 12 …** | `BEATS_PER_SONG = 3` | `GameStats.beaten_count(game)` |
| for **every 5 distinct goals** completed there: 5, 10, 15 … | `GOALS_PER_SONG = 5` | `GameStats.distinct_goals_count(game)` (everything in `GameStats.goals_at(game)`) |

So beating a game once earns 1 song, three times 2, six times 3; and its 5th
distinct goal earns one more on top, whatever the beats are. Each song earned is
**drawn at random from that game's songs still locked**. A game with no locked
songs left draws nothing (the songs it is owed wait, and a row added to the sheet
for it later is drawn at once). Songs **whose file is in the folder are drawn
first**, so an unlock is something that plays whenever there is one to give.

**A game's first song is its menu song.** When a game draws its first song and
one of its songs is tagged `menu`, that is the song it draws: the first Hades
song is always Hades's menu song. The rest of the game's songs are drawn as
above after it.

- **With several menu songs**, one of them is drawn first (at random, its file
  in the folder first); the others are ordinary songs of the game after that.
- **A menu song whose file is missing is still first.** The game's first song
  is its menu song either way; it shows as "file not found" until the file is
  in the folder.
- **A game that already has a song** (a save from before this rule) draws no
  menu song first: its menu song is in the draw like the rest.
- **A game with no menu song** draws its first song from all of them, as
  before. Another game's menu song is never drawn for it.

A locked song's line in the list says what **its game** needs for its next song
("Next Hades song: beat Hades 2 times more, or complete 3 more distinct goals
there"). It is the game that is close, not the song: which one comes up is luck.

**Every kind of goal counts:** the character's level-up, enemies, bosses,
weapons, standing status goals, bonus clauses and curses followed. Doing the
same goal again (re-clearing Monkey, charging the same Whip) doesn't move it; a
new one does. **A bonus counts once per status**: Burn paid on two different
enemies is one goal. **Event goals are not on the record at all** (the owner's
call: there is one in the game, and it is not worth a section). They are still
claimed in a run as before; they just don't count or show here.

### Where each kind is recorded

`GameStats.goals_at(game)` reads three logs as one list, in the order a game's
Collection page shows them (`GameStats.GOAL_KINDS`): Character, Enemies,
Bosses, Weapons, Statuses, Bonuses, Curses.

| Kind | Log | Same goal = same… |
|---|---|---|
| Character | `levelup_log[game][character]` | character |
| Enemies / Bosses | `enemy_log[game][enemy]` (split by `Data.get_boss`) | enemy |
| Weapons, Statuses, Bonuses, Curses | `goal_log[game][kind][key]`, written by `GameLoop2.record_completed_goal(kind, text, key, label)` | weapon id / status id / status id / curse id |

`goal_log` is new with this change, so goals of those four kinds done before
it don't appear; level-ups and enemies go back to the start of the save.

The radio **stores no progress of its own**: the beats and goals are GameStats's.
What it keeps (per profile, `radio.json` in the profile folder) is **the draw**,
which songs came up, because a random pick cannot be worked out again from the
counts the way a per-song rule could. Each draw gets its toast and jumps the
queue exactly once. **Nothing is ever locked again**: a save from before the
random rule keeps every song it had, even if its counts would now earn fewer
(its old `radio.json` listed them as "announced", and that list is read as the
songs it holds).

- **Re-checked on every `GameStats.changed`**, which a report always emits.
- **It only starts music by itself when there is a window** (`Radio.autoplay`).
  Headless, which is how the test suite runs, nothing plays until a control is
  pressed: the suite shares `user://` with the real game, and used to play the
  owner's music during a test run.
- **At boot and on a profile switch, unlocks are taken quietly.** A first launch
  on an old save could otherwise owe dozens of toasts.
- **An unlocked song whose file isn't in the folder** is listed as "file not
  found" and skipped. A typo in `File` then shows up as a typo, not as a song
  that silently doesn't exist.

## 4. Playing it: the game keeps the clock

The music can come out of two speakers: `radio.html` in OBS, or the game window
(an `AudioStreamPlayer` on the `Radio` node). **The OBS page can't talk back.**
There is no server; the game only writes a file the page reads
(`ObsCompanion`). So the page can't say "this song ended", and the radio keeps
time itself:

- **At the start of each track** the stream is loaded and its length read
  (`get_length()`). This is also why only mp3/ogg/wav are supported: those are
  the formats Godot can load at runtime and measure.
- **The position** is `offset + (now - since)` while playing, and `offset` while
  paused.
- **When the position passes the length**, the radio moves on.
- **The page is told** the track, `offset`, `since` (unix seconds), whether it is
  playing, and a `seq` number that moves on every start, restart, pause and
  resume. It seeks when `seq` changes, and otherwise only corrects drift of more
  than 2 s.
- **A refreshed OBS source** picks the song up where it is.

Nothing in the payload moves between changes, so `ObsCompanion`'s dedupe still
treats an unchanged radio as unchanged. The page works out the running position
from `since` on its own.

**One speaker at a time, chosen by a setting.** The page can't tell the game
it's open, so "play in the game when OBS isn't running" can't be detected. The
other speaker stays silent so nothing ever plays twice. For the same reason
**only `radio.html` plays**: every view is the same page, and a scene with the
checklist, the map and the timer in it would otherwise play the music three
times over, out of step.

**The track is staged beside the page** (`user://obs/radio/`, only the current
one kept), for the reason the covers are: nothing the page loads may point
outside its folder, or OBS's browser source refuses it (README, "The stream
overlay").

## 5. The queue

- **Shuffle** (the default) deals every playable song on the station once
  before any repeats. The song just played never opens the next pass.
- **In order** walks the catalog in id order.
- **A new unlock** is pushed onto the front of the queue.
- **Back** restarts the song if it is more than 3 s in; otherwise it goes to
  the previous song (a history of 50).
- **A station** (a tag) filters the playable list. "All songs" is no filter.
  **★ Favourites** is a station too (§5a).
- **A file that won't decode** is skipped, and remembered for that pick so a
  folder of broken files ends in silence rather than a loop.

## 5a. Favourites

The owner's choices, asked before it was built:

- **It is a station**, not a switch: "★ Favourites" is the second entry in the
  station list, after "All songs" (its value is `Radio.FAVORITES`, `*favorites`,
  which no tag can be: the generator refuses a tag starting with `*`). It can't
  be combined with a tag; it uses the same queue and shuffle as any station.
- **Stars belong to the profile**, like the songs it has drawn, and are saved
  beside them in `radio.json` (`"favorites"`).
- **Only an unlocked song can be starred.** The ★ is on each unlocked song's row
  and beside the title of the song playing; gold when starred, faint when not.
- **Stars change nothing else.** Normal shuffle still plays every song once
  before any repeats.
- **The overlay shows it.** The payload's `song.favorite` puts a ★ before the
  title on the `radio.html` card. Display only: the page can't be clicked.
- **Un-starring the song that is playing lets it finish**; it just isn't picked
  again. **Starring a song while the Favourites station stands silent** starts
  it.
- With no favourites, the station is silent and the screen says "No favourites
  yet. Click the ★ on a song below."

## 6. Where the controls are

`RadioScreen`, opened from **📻 on the run's header bar** (beside Map and Menu,
on the layer no modal covers) and from **Radio in the main menu's top-right
corner**. It has:

- what's playing and how far in;
- Back / Pause / Skip and a volume slider;
- a ★ beside the title of what's playing, to star or un-star it;
- shuffle, the station (★ Favourites among them), and where it plays from;
- the music folder, with Open folder, Rescan (for files added while the game
  is running) and Export song list (§2a);
- every unlocked song, with a ★ to star it and a ▶ to play it now; then **one
  row per game for its locked songs** ("Balatro — 4 songs locked"), the game
  nearest its next song first, saying what that game still needs ("Next
  Balatro song: beat Balatro once more, or complete 2 more distinct goals
  there", with where its goals so far came from).

**The list is built for a whole library.** The owner's sheet has over a
thousand songs, and a row each cost three seconds to open the screen and three
more on every new track. Locked songs collapse per game (which one comes next
is luck, so the game is what is worth reading), and the list is only rebuilt
when what it shows moved: a new track rebuilds just the two rows the "playing"
mark moved between.

The speakers, volume, shuffle, station and pause live in `user://radio.cfg`.
They belong to the PC, like the window mode does, not to a profile.

## 7. Setting it up (for the streamer)

1. Put the music in the folder the Radio screen shows (`Open folder`).
   Subfolders are fine, and a folder named after its game is how that game is
   found.
2. Press **Export song list** and upload `tools/radio_import.json`; then
   `python3 tools/apply_radio_import.py` writes the rows and regenerates (§2a).
   A single song can still be typed into the `radio` sheet by hand.
3. In OBS, add a Browser Source with "Local file" ticked, pointed at
   `radio.html` in the overlay folder, sized about 352 × 100.
4. In OBS's Advanced Audio Properties, set that source's Audio Monitoring to
   **Monitor and Output** to hear it yourself. Untick it on the VOD track if the
   music shouldn't be in the recording.

## 9. The game's Collection page

A game's page is **520px wide** (`Collection.GAME_DETAIL_PANEL_W`); every other
tab's card keeps 360. Its two lists are grids of pictures:

- **Influenced / Influenced By**: the games' covers, the name (and year) on the
  hover. A click opens that game's page. The covers are drawn a few per frame
  (`Collection.COVERS_PER_FRAME`), so a game that influenced sixty others opens
  at once and fills in over a few frames instead of stalling on sixty decodes.
- **Goals completed here (N)**: a header per kind in `GOAL_KINDS` order, only
  the kinds that have something in them. N is the radio's count (every
  picture in the section), and Enemies keep their "(beaten / can appear here)" figure. Each goal is
  its art (the enemy, the character's icon, the weapon, the status, the
  curse) with **the times done in the top-right corner**. The hover carries
  the name and "beaten / levelled / done / followed ×N", the goal itself, and
  your note. A click on an enemy, boss or level-up opens its note editor; the
  other kinds have no note. A goal with no art shows its name instead.
